# Dirigent

- The service and app are dogfooded, make sure to not kill the process you are running in.
- Test the UI only through `scripts/ui.sh`: it runs a debug build on its own invisible display, port and data dir, so you can't disturb users desktop or data (see `testing.md`).
- Never `pkill -f <string>` from a shell whose own command line contains `<string>` — you kill your shell. Anchor patterns with `^/abs/path`.
- `dirigent_service` is a lib + bin. The desktop embeds the lib and runs the local service in-process; the binary is only for remote hosts. `dirigent_cli` is the `dirigent` command line: `dirigent pi …` (the bundled pi's CLI), `dirigent [dir]` (execs `dirigent_desktop` next to it). `packaging/README.md` has it.
- Pi's agent dir (auth, settings, packages, extensions) is `<config dir>/agent`, not `~/.pi/agent`: `PI_CODING_AGENT_DIR` for the runtime (`runtime_env`), seeded by copying an existing one on first use (`agent.rs`). A test instance's `--config-dir` gets a copy of Seb's real one, auth included.
- `dirigent_api` is the update api on Seb's server (and the leaderboard's: `leaderboard.rs`, with its only state, a sqlite db) and the release workflow's `publish`. Desktops talk to `https://dirigent.sebba.dev` in every build; `DIRIGENT_API_URL` points a test instance at a local `dirigent_api serve` instead. The leaderboard account lives in the data dir, so a test instance starts signed out and uploads nothing; so does the forge sign-in (`<data dir>/forge.json`, `dirigent_service/src/forge.rs`): test it against a local forge only (`DIRIGENT_FORGE_URL`, `DIRIGENT_FORGE_CLIENT_ID`; testing.md), and don't copy a real `forge.json` (a credential: the copy acts as Seb's forge account); `packaging/` has the Windows installer and the Linux install script. How releases and updates work, and what must stay compatible for installs in the field: `packaging/README.md`. The version is `[workspace.package] version`; releases run by hand (`.github/workflows/release.yml`).
- One desktop per data dir: a second launch hands its folder to the running one and exits (`instance.rs`, keyed on `<data dir>/desktop.port`). Always pass `--data-dir` to a desktop you start by hand, or it hands off to Seb's.
- `flake.nix` also packages the binaries for nix (`packaging/README.md`). Changing `Cargo.lock` or `bun.lock` changes a hash there: bump it (`lib.fakeHash`, then `nix build .#dirigent_service` prints the right one).
- Never set `DIRIGENT_BUILD_UPDATE_URL` outside the release workflow: it bakes the update url into the binary. Tests use `DIRIGENT_UPDATE_URL` at run time.
- Seb's data is live: an existing `service.db` / `desktop.db` must open with the new code. Schema changes are additive and self-applying (`CREATE TABLE IF NOT EXISTS`, `ensure_column` in `storage.rs`); new wire fields get `#[serde(default)]`. No version bumps. Test dbs can be wiped freely (`scripts/ui.sh reset`). `--data-dir` / `--config-dir` (both binaries) point an instance away from the real dirs.

## Checks before you're done

`cargo fmt --all`, `cargo clippy --workspace`, the Windows `cargo clippy` above when you touched platform code, `cargo test --workspace`, `bun run typecheck`, `bun run lint`, `bun run fmt`.
