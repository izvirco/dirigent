# Dirigent

- The service and app are dogfooded, make sure to not kill the process you are running in.
- Test the UI only on your private screen (the `computer` tool), with the debug build `scripts/ui.sh` starts there on its own port and data dir, so you can't disturb users desktop or data (see `testing.md`). Never on the desktop.
- Never `pkill -f <string>` from a shell whose own command line contains `<string>` — you kill your shell. Anchor patterns with `^/abs/path`.
- `dirigent_service` is a lib + bin. The desktop embeds the lib and runs the local service in-process; the binary is only for remote hosts. `dirigent_cli` is the `dirigent` command line: `dirigent [dir]` (execs `dirigent_desktop` next to it), `dirigent key …`, `dirigent login`. `packaging/README.md` has it.
- A `dirigent_service` on its own updates itself when a desktop tells it to (`dirigent_service/src/update.rs`, which the desktop's own update uses too). `install.sh --headless` registers it with systemd or launchd: never run that as yourself on this machine, it would start a service on Seb's data (`testing.md` has how to try it).
- `dirigent_agent` is the agent, a library the service embeds: the sessions and their run loop, the tools, codemode (QuickJS), MCP servers, and the client of the one way to a model, a CLIProxyAPI the user runs (Anthropic Messages for Claude, Codex Responses for the rest). `dirigent_agent/DESIGN.md` has how it hangs together. A thread's history is `dirigent_protocol::transcript`'s entries, the same in memory, in the db, on the wire and in the UI.
- A reply's `visual` blocks (`dirigent_protocol::visuals`: HTML and CSS a model writes to show a chart or a diagram) are drawn by Blitz, on the CPU, into a picture (`dirigent_desktop/src/visual.rs`). No scripts, no network. Stylo, Blitz's CSS engine, runs python in its build script: the dev shells have it, a build outside them needs a `python3`.
- The agent's files: `<config dir>/agent.toml` (compaction, MCP servers; owner-only, and with no key of Dirigent's in it, so that users can share it between machines), `<config dir>/AGENTS.md` (the user's instructions) and `<config dir>/skills/`; `<data dir>/mcp-auth.json` (MCP sign-ins) and `<data dir>/proxy.json` (the host's proxy: its address, API key and management key; owner-only). A test instance's `--config-dir` starts with a copy of Seb's real ones, and its data dir with the proxy's address and API key (`dirigent_service/src/agent.rs`). Test with `claude-haiku-5-5` and short prompts: the proxy is Seb's subscription.
- Dirigent used to run pi (a TypeScript agent harness, as a bundled runtime), up to 0.0.9. 0.0.10 migrated an install on its first start, and that migration is gone: a `service.db` as pi left it is refused (`Storage::open`, which says to start 0.0.10 on it once). What is left of pi is in the data: threads 0.0.10 could not convert whole are `locked` (they open and fork, but take no message), and stored efforts may be pi's (`off`, `minimal`).
- `dirigent_api` is the update api on Seb's server (and the leaderboard's: `leaderboard.rs`, with its only state, a sqlite db) and the release workflow's `publish`. Desktops talk to `https://dirigent.sebba.dev` in every build; `DIRIGENT_API_URL` points a test instance at a local `dirigent_api serve` instead. The leaderboard account lives in the data dir, so a test instance starts signed out and uploads nothing; so does the forge sign-in (`<data dir>/forge.json`, `dirigent_service/src/forge.rs`): test it against a local forge only (`DIRIGENT_FORGE_URL`, `DIRIGENT_FORGE_CLIENT_ID`; testing.md), and don't copy a real `forge.json` (a credential: the copy acts as Seb's forge account), nor a `proxy.json` beside it (it has a host's CLIProxyAPI management key, which opens every account behind the proxy; a test instance gets the address and the API key by itself, and needs no more to run threads); `packaging/` has the Windows installer and the Linux install script. How releases and updates work, and what must stay compatible for installs in the field: `packaging/README.md`. The version is `[workspace.package] version`, in draft on master: a nightly is a prerelease of it named by its build time (`0.0.10-nightly.202611151432`), baked in as `dirigent_protocol::release::VERSION`, which is what code reads, not `CARGO_PKG_VERSION`. A nightly build is Dirigent Nightly, an app of its own next to a stable install that shares nothing with it (dirs, port, command, icon: the table in `packaging/README.md`): anything new that an install keeps outside its data and config dirs needs a nightly name too (`release::app`). Releases run by hand (`.github/workflows/release.yml`).
- One desktop per data dir: a second launch hands its folder to the running one and exits (`instance.rs`, keyed on `<data dir>/desktop.port`). Always pass `--data-dir` and `--config-dir` to a desktop or service you start by hand: without the first a desktop hands off to Seb's, and with only one of them the other directory is Seb's real one (with only `--data-dir`, a start moves the proxy out of Seb's real `agent.toml` into that data dir, and a 0.0.10 running on it has no proxy).
- `flake.nix` also packages the binaries for nix (`packaging/README.md`). Changing `Cargo.lock` changes a hash there: bump it (`lib.fakeHash`, then `nix build .#dirigent_service` prints the right one).
- Never set `DIRIGENT_BUILD_UPDATE_URL` outside the release workflow: it bakes the update url into the binary. Tests use `DIRIGENT_UPDATE_URL` at run time. `DIRIGENT_BUILD_VERSION` bakes the version in the same way; only set it to test a nightly build (`testing.md`).
- Seb's data is live: an existing `service.db` / `desktop.db` must open with the new code, and a stored entry (`transcript::Body`, as JSON) must read. Schema changes are additive and self-applying (`CREATE TABLE IF NOT EXISTS`, an `ALTER TABLE … ADD COLUMN` run unless the column is there); new wire fields get `#[serde(default)]`. No version bumps: `dirigent_protocol::PROTOCOL` only moves when an older peer could not read what a newer one sends at all. Test dbs can be wiped freely (`scripts/ui.sh reset`). `--data-dir` / `--config-dir` (both binaries) point an instance away from the real dirs.
- No `mod.rs`: a module with submodules is `x.rs` beside its `x/` directory (`dirigent_agent/src/tools.rs` and `tools/`).

## Checks before you're done

`cargo fmt --all`, `cargo clippy --workspace`, the Windows clippy (`nix develop .#windows -c cargo clippy --workspace --target x86_64-pc-windows-gnu`) when you touched platform code, `cargo test --workspace`, `oxlint`, `oxfmt` (the dev shell has both: they take the scripts, `dirigent_agent/src/codemode/prelude.js` and the markdown).
